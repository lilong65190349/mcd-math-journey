# 模块化设计方案 · 故事线与题库解耦（含学科扩展）

> 目标：把「故事线」与「题库」拆成独立可复用模块，并让系统能接入语文、英语等新学科。
> 本文分为四段：**现状说明 → 目标架构 → 扩展流程 → 迁移分期**。
> 所有结论均基于当前仓库实际数据与代码（`data/`、`scripts/`），关键处标注文件与行号。

---

## 一、现状：数据结构与内容组织方式

### 1.1 当前有四个数据域 + 一个装配器

```
data/
├── storylines/
│   ├── index.json        1.5 KB   故事线注册表（5 条，含 available 上线闸门）
│   └── {xiyou,sanguo,silu,zhenghe,shuihu}.json   ~20 KB/条   故事线本体
├── characters/
│   └── {同上 5 个}.json    ~7.6 KB/条   角色库（每条 14 名）
├── curriculum.json        15.7 KB  知识点图谱（4 个年级 / 25 个知识点）
└── run_rules.json         2.8 KB   闯关规则参数（品阶阈值、题数权重、彩蛋配置）

scripts/
├── problem_gen.py         1831 行  装配器 + 9 个题型模板
├── journey.py              605 行  闯关规则引擎（解锁 / 抽题 / 品阶 / 收卡）
├── verify.py               394 行  判分 + 错因归因 + 讲解
├── selfcheck.py           1657 行  文档与代码一致性自检

**规模基线**：5 条故事线 × 9 关 × 9 难 = **405 个关卡位**；70 名角色；25 个知识点（实际被用到 14 个）。

### 1.3 当前的数据流：一条隐式契约撑起全部

```
level.kp_id ──→ curriculum.kps[id] ──→ grade / kp_name        （显式外键，正常）
stage.stage ──→ _TEMPLATES[1..9]     ──→ 用哪个题型模板        （隐式契约，问题所在）
```

装配器 `problem_gen.generate()`（1636-1801）的组装逻辑：
1. `resolve_level()` 定位关卡 → 拿到 storyline 的 `stage` 与 `level`
2. `_ctx()`（602-635）把 `role`（来自 `role_focus`）、`scene`、`story`、数据池塞进 ctx
3. **`int(stage["stage"])` 当作 `_TEMPLATES` 的键**（1734-1736）→ 决定跑哪个模板
4. `kp_map[kp_id]` 取知识点与年级（1762-1786）
5. 模板返回 body，`generate()` 拼成题目对象

**⚠️ 核心事实：模板只靠 `stage` 整数选，与故事线、知识点、难度都无关。**

模板函数体内**从不读取** `story_id` / `story_name`，只用两个字符串：
- `ctx["role"]` ← `level.role_focus or roles["review"]`（628）
- `ctx["scene"]` ← `level.scene`（632）

这就是「加故事线不用改代码」能成立的原因——**但反过来，故事线也只能影响这两个词**，无法影响题型、数据表结构、答案类型。

### 1.4 现状的六个耦合问题（带证据）

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| **C1** | **题型键是关号，而非能力标签** | `_TEMPLATES[1..9]`（1439-1449）；分发 `int(stage["stage"])`（1734） | 语文第 1 关与数学第 1 关都要 `key=1`，**键空间直接冲突** |
| **C2** | **`op_family` 已填好却被闲置** | 5 条线 45 关全部填了 `op_family`（add/sub/mul/div/decimal/time/percent/average/discount），实测 **关号↔op_family 完全一一对应，零例外**；但代码只在 `list_stages` 里输出它（problem_gen.py:490） | **一个现成的语义键躺在数据里没被用** —— 这正是解耦的免费切入点 |
| **C3** | **没有学科维度** | `subject` / `学科` / `SUBJECT` 在 `scripts/` 与 `data/` 中 **0 命中** | 语文/英语无处安放 |
| **C4** | **知识点是全局平表** | `kp_index()`（455-467）返回 `{kp_id: …}` 单层；`load_curriculum()`（335-338）只读一个文件、只认 `grades` 键 | 数学与语文同年级题会被 `--grade` 混在一起 |
| **C5** | **答案语义是数值专用** | `_answer_value()`（1495）只认 `Decimal` 与 `a/b` 分数；`answer_type` 只有 `number/percent/fraction` | 语文答案「白日依山尽」→ `_answer_value` 返回 `None` → `_answer_targets` 空 → **`_hint_leaks()` 直接 return False，「提示不泄露答案」这道防线静默失效且不报错**（最隐蔽、后果最重） || **C6** | **聚合数字硬编码** | `405` 在 `demo/index.html` 硬编码 **4 处**；`selfcheck.py` 断言「405 题 / 70 名角色」；README 多处写 405 | 加一条线 → 405 变 486 → **必须改代码**，「零改动加故事线」实际上不成立 |

**另外两处设计债**（本次一并解决）：

- **C7 角色双源无一致性断言**：`storylines.roles` / `stage.role_focus` 与 `characters.characters[].name` 是两套名字，靠人工对齐，`selfcheck` 只校验角色库自身，**不校验两者同名** → 极易出现「题目里是猪八戒、闯关大将是别人」。
- **C8 知识点闲置**：25 个 kp 只用 14 个，`g3_mul_basic` / `g6_circle` 等 11 个**没有任何关卡引用** → `--kp` 传这些 id 会 exit=2（工程师在技能包阶段踩到过）。

### 1.5 C5 的实测证据（这条不是推断，是跑出来的）

```python
>>> problem_gen._answer_targets("白日依山尽", "text")
[]
>>> problem_gen._hint_leaks("提示：答案是白日依山尽", "白日依山尽", "text")
False          # ← 答案原样写进提示，检查器仍判定「不泄露」
```

| 答案 | answer_type | `_answer_targets` | `_hint_leaks`（提示里明写答案） |
|---|---|---|---|
| `白日依山尽` | text | `[]` | **False** ❌ |
| `apple` | text | `[]` | **False** ❌ |
| `孙悟空` | text | `[]` | **False** ❌ |
| `200` | number | `[Decimal('200')]` | 正常按数值比对 ✅ |

**结论：对文本答案，这道检查是「彻底失效」而不是「部分失效」** —— 它不报错、不警告，静默放行一切。若直接接语文/英语而不先扩展判分，**整个「提示不泄露答案」机制会在一夜之间变成装饰**，且无人察觉。

## 二、设计目标与原则

| 原则 | 含义 | 对应解决 |
|---|---|---|
| **P1 一条外键** | 故事线与题库之间**只允许存在一个耦合点**：`kp_id` | C1 / C2 |
| **P2 故事线只管叙事** | 故事线不出现任何学科、算法、判分信息 | C3 |
| **P3 学科正交于故事线** | 同一条故事线可同时出数学题和语文题 | C3 / C4 |
| **P4 学科是知识点的属性，不是关卡的属性** | `subject` 由 `kp_id` 推导，`level_id` 语法不变 | 向后兼容 |
| **P5 数量从数据算，不写死** | 所有聚合数字动态计算 | C6 |
| **P6 加东西只加文件，不加分支** | 新增故事线/学科走「加数据 + 注册」，不改装配逻辑 | 可维护性 |

## 三、目标架构：四模块 + 一装配层

### 3.1 模块划分与职责边界

| 模块 | 唯一职责 | 数据/代码位置 | **明确不管什么** |
|---|---|---|---|
| **storyline**（故事线） | 叙事外壳：线元信息、9 关的地名/事件/主题/角色焦点、每关 9 难的 `kp_id` 引用与题面摘要 | `data/storylines/*.json` | 不管题型、公式、数据表结构、判分、学科 |
| **curriculum**（知识点） | 知识点图谱：按 **学科 × 年级** 组织，含课标依据、能力标签 `skill` | `data/curriculum/<subject>.json` | 不管叙事、不管实现算法 |
| **template**（题型库） | 题型模板：按 `(subject, skill)` 索引，负责算题、出数据表、给答案、写提示与讲解 | `scripts/subjects/<subject>/templates.py` | 不管关号、不管故事线是谁（只吃 `role`/`scene` 字符串） |
| **datasource**（数据池+判分） | 数据三级降级（MCP→缓存→示例）、判分、错因归因、讲解渲染 | `scripts/data_source.py`、`verify.py` | 不管题材、不管学科 |
| **装配层**（problem_gen） | 把四方组装成题目对象：定位关卡 → 解析知识点 → 按 `(subject, skill)` 取模板 → 合并输出 | `scripts/problem_gen.py` | **不做业务计算、不做叙事创作** |

### 3.2 关键决策一：题型键从「关号」改为「(学科, 能力)」

```
现在：  _TEMPLATES[stage]                      int 1..9，全局单命名空间
改为：  TEMPLATES[(subject, skill)]            ("math","add") / ("chinese","poem_fill")

其中 skill 就是数据层已填好的 op_family（数学），新学科自带自己的 skill 词表。

> **⚠️ 实施期修订（2026-10-25，架构师实测指出，本文原表述有误）**
>
> 上文与 §3.4 关系图容易读成「派发键 = `kp.skill`」，**这是错的**。
> 实测 `kp → stage` **不是单值映射**：`g6_percent` 同时被第 7 关（`op_family=percent`，15 个关卡位）
> 和第 9 关（`op_family=discount`，**45 个关卡位**）引用。若用 `kp.skill` 派发，
> 第 9 关这 **45 个关卡位会被静默错派到百分数模板**，而不是折扣模板。
>
> 正确做法是**三级 fallback**：
> ```python
> skill_of(level, stage, kp) = level.skill or stage.op_family or kp.skill
> ```
> 旧线（有 `op_family`）走第二级、新线（不写 `op_family`）走第三级 `kp.skill`，两条路径殊途同归，
> 且原有 405 题逐字节不变（已用 `git show baseline-405:demo/bank.json` 逐题比对验证，0 差异）。
>
> **这条修正的价值**：设计文档里的「等价替换」结论只对 `stage → op_family` 成立，
> 不能外推到 `kp → skill`。**任何"可以等价替换"的判断，都要先验证映射的方向是否单值。**
```

**为什么这一改是安全的**：实测 5 条线 45 关的 `stage → op_family` 是**严格一一映射**（1→add / 2→sub / … / 9→discount），所以
```python
TEMPLATES[("math", stage.op_family)]  ≡  _TEMPLATES[stage.stage]
```
**迁移期零数据改动、零行为变更**，可先做等价替换，再逐步废弃 legacy 键。

### 3.3 关键决策二：`subject` 不进 `level_id`

**学科是知识点的属性，不是关卡位置的属性。**

```
level_id 语法保持：<story>-<stage>-<difficulty>   （默认线仍可简写 1-1）
subject 推导：      subject = curriculum.subject_of(level.kp_id)
```

好处：
- **零破坏**：现有 405 个 `level_id`、CLI 参数、URL、题库快照全部不用动
- **天然支持混排**：同一关下不同难度可以挂不同学科的 `kp_id`（`1-1` 数学、`1-2` 语文），装配层按 `kp_id` 自动路由
- **避免 C4 的 `--grade` 混淆**：`--grade` 改为 `--subject math --grade 4`，学科先过滤

### 3.4 模块间关联关系（唯一外键）

```
        ┌─────────────────────────────┐
        │ storyline（叙事外壳）        │
        │  9 stages × 9 levels         │
        └──────────────┬──────────────┘
                       │  level.kp_id        ← 唯一外键
                       ▼
        ┌─────────────────────────────┐
        │ curriculum（知识点图谱）      │
        │  kp.subject / kp.grade       │
        │  kp.skill（能力标签）         │
        └──────────────┬──────────────┘
                       │  (subject, skill)
                       ▼
        ┌─────────────────────────────┐
        │ template（题型库）            │
        │  TEMPLATES[(subject, skill)] │
        └─────────────────────────────┘

        datasource（数据池+判分）── 被 template 消费，与上面三者都不耦合
```

**一句话**：故事线指向知识点（外键），知识点带出（学科, 能力），能力选中模板。**故事线永远不知道谁在出题。**

## 四、扩展流程（最小改动）

### 4.1 新增一条故事线 —— **零代码改动，只加 3 个文件**

以《哪吒闹海》为例：

| 步骤 | 动作 | 文件 |
|---|---|---|
| 1 | 复制现有一条线改内容：9 关 × 9 难，每关写 `name/theme/scene/role_focus/grade_hint`，每难写 `level_id/kp_id/brief` | `data/storylines/nuozha.json` |
| 2 | 写 14 名角色：9 名闯关大将（`stage_bosses` 1~9）+ 5 名守关池（`guard_pool`） | `data/characters/nuozha.json` |
| 3 | 注册表加一项（`id/name/subtitle/file/available:true/era_note`） | `data/storylines/index.json` |
| 4 | 重新导出演示题库 | 跑 `python scripts/export_demo_bank.py --offline` |
| 5 | 自检 | `python scripts/selfcheck.py` |

**代码改动：0 行**（前提是完成第 3 期迁移把聚合数字动态化，见 §5）。数学知识点直接复用现有 25 个 kp，`kp_id` 照抄即可。

**唯一需要人工把关的**：`role_focus` 必须与 `characters[].name` 同名（C7）。建议自检加一条断言自动校验，从此不用人工。

### 4.2 新增一个学科 —— **加 3 个文件 + 1 个注册项，装配层不动**

以语文为例：

| 步骤 | 动作 | 文件 |
|---|---|---|
| 1 | 写知识点图谱：`subject/chinese`，每个 kp 必须带 `skill`（如 `poem_fill` / `pinyin` / `reading_comp`） | `data/curriculum/chinese.json` |
| 2 | 写题型模板：按 `skill` 组织，每个模板签名为 `fn(ctx) -> body`（与现有 9 个模板同构），返回 `question/answer/answer_type/hints/steps/verify` | `scripts/subjects/chinese/templates.py` |
| 3 | 声明答案类型：文本类需要 `answer_type: "text"` / `"enum"` | 上表 `answerTypes` |
| 4 | 注册表加一项 | `data/subjects/index.json` |
| 5 | 让某条故事线的 `levels[].kp_id` 指向语文知识点（**故事线文件本身不用改结构**，只换 kp_id） | 对应 storyline json |

**装配层 `problem_gen.py`：不改**（它只按 `(subject, skill)` 查表）。

**⚠️ 必须同步做的两件事（否则静默失效）**：

1. **扩展判分**：`verify.py` 增加 `text` / `enum` 类型的比对（去空白、全半角归一、可选同义词表）。**不改的后果**：`_answer_value()` 返回 `None` → `_hint_leaks()` 静默 `return False` → **「提示不泄露答案」这道防线整体失效且不报错**（C5，最危险的一处）。
2. **放宽 `data_table` 必填**：现在 `generate()` 强取 `body["data_table"]`（1772）→ 无表格题型（如古诗填空）会崩。改为可选，无表格时不渲染表。

### 4.3 二者组合：复用矩阵（解耦的真正收益）

因为 P3「学科正交于故事线」，两个维度可以自由组合：

| | 数学 | 语文 | 英语 |
|---|---|---|---|

## 七、结论

1. **现状不是「没有结构」，而是「结构错位」**：故事线数据其实已经很干净（只提供关名/地名/角色/brief 四个字段），问题全在**代码层用关号当题型键**（C1），以及**缺学科维度**（C3）。
2. **解耦的切入点几乎是免费的**：`op_family` 这个语义键**已经填在数据里、且与关号严格一一对应**（实测 45 关零例外），只是代码没用它。把它换成派发键，即可零风险完成核心解耦。
3. **学科不进 `level_id`** 是关键取舍，换来的是 405 个现有 `level_id`、CLI 参数、题库快照全部不用动，且天然支持同一关混排多学科。
4. **完成 P1+P2（约 1 天）即可交付「故事线与题库解耦」**；新增故事线届时**零代码改动**；新增学科只需加 3 个文件 + 1 个注册项 + 扩展判分。
5. **不建议今晚赶工**：框架改造 1 天 + 两条故事线 1.5 天 + 一门学科 3 天，远超剩余时间。建议今晚守住现有 405 题的可提交状态，把本方案作为赛后第一优先级迭代。
